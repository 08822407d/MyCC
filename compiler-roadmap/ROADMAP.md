## 每个阶段的理由和注意事项

### 阶段 1：C 子集前端（OCaml → LLVM IR）

**为什么用书而不是自己划范围**：C 的完整实现有大量**不可迁移**的成本
（声明符螺旋规则、typedef 歧义导致的 lexer hack、整型提升规则表、数组/函数退化）。
这些学到的是「C 的规定」不是「编译器的原理」。用书把范围钉死，避免失控。

**关键决策：完全跳过预处理器。** 直接用 `gcc -E` 预处理，你的编译器吃 `.i` 文件。
理由见下面的「明确排除的方向」。

**关键技巧：不要碰 LLVM 的 OCaml binding。** 直接输出文本 `.ll`，然后 `clang foo.ll -o foo`。
接口就是一个文本文件，绕开整个 C++ API 和 opam 装 llvm 包的版本地狱。

**关键技巧：不要自己构造 SSA。** 局部变量一律 `alloca` + `load`/`store`，
一个 phi 节点都不写，交给 LLVM 的 `mem2reg` 自动提升（`clang -O1` 即可）。
这是 LLVM 官方教程的标准做法，能砍掉约 30% 的难度。

**前置条件**：装 LLVM 工具链（`sudo apt install clang llvm`）。**2026-08-05 实测两台机器都没装。**

**估算**：IR 生成之外的胶水代码约 300–450 行、一周；调试再加 1–2 周。

### 阶段 1.5：优化 pass

补中端缺口。整条路线里如果缺了这一段，会**只会写前端和后端、不懂中间**，
而中间恰恰是当前最值钱的部分。做完这一步才会真正理解 SSA 为什么存在。

### 阶段 2：Harvard CS153

**技术栈高度契合**：OCaml 实现，源语言是 **LLVMlite**（64 位 LLVM IR 的简化子集），
目标是 **X86lite**（理想化的 x86-64 子集），共 8 个作业，
而且**前置作业要求先自己写 X86lite 的汇编器和模拟器**——这个设计逼你搞清楚指令编码和执行模型。

**它不涉及面向对象**，OO 那块靠阶段 4。

### 阶段 2.5：重定向到 RISC-V

**整条路线里认知密度最高的单个练习。** 把一个能跑的后端从 x86-64 迁到 RISC-V，
会逼你分清「哪些是通用概念、哪些是 ISA 特产」——这个认知只有做过一次迁移才拿得到。

⚠️ **2026-08-05 查证：RISC-V 目前没有 canonical 的代码生成教学课。**
现有材料（CGO 论文、LLVM 工程博客）是给已经懂的人看的。所以必须走「在 x86-64 的课上学概念 → 自己迁移」这条路。

### 阶段 3：Cornell CS 6120

Adrian Sampson 的博士生课程，**官方提供免费自学版**（视频 + 讲义 + 开放式实现任务）。
用 Bril（教学 IR）+ LLVM，**任务语言无关**，可以用 OCaml 做。

内容正好是 2026 年最抢手的技能（IR 设计 + 数据流分析）。

### 阶段 4：面向对象编译器

**用户在这块有巨大的隐藏优势**（见 `skills-profile.md`）：
内核的 `struct file_operations` 就是手写 vtable，他已经手写了六年。
要学的只是「编译器怎么自动生成」，跨度比普通学生小得多。

候选材料：

- **《Crafting Interpreters》第三部分（clox）** ← 推荐。免费在线，C 写的字节码虚拟机，
  实现的 Lox 是**类式 OO 语言**（含继承和方法分派）。同时命中他的 C 强项和 OO 目标，没有 MIPS 包袱。
- **Stanford CS143 的 Cool 类型系统部分** ← 只取材料，不上整门课。
  Cool 有**真正的子类型系统**（`SELF_TYPE` 尤其刁钻），这是 C 完全给不了的东西。
  **但它的代码生成目标是 MIPS，不要做那部分**（理由见「已推翻的判断」）。

### 阶段 5：转 C++

**概念已具备，纯工具切换。** 需要补的 C++ 子集不大：
`std::variant` + `std::visit`（对应 OCaml 的代数数据类型）、`unique_ptr`/移动语义、RAII、基础模板。

**顺序对他有利**：先在 OCaml 里习惯 ADT + 模式匹配，回到 C++ 时会**有意识地**
用 `std::variant` 建模 AST，而不是虚函数继承体系——很多 C++ 编译器工程师是吃了苦头才学会这一点的。

## 明确排除的方向

### C 预处理器：读懂，不实现

**理由**：它的复杂度**全部来自向后兼容，不来自问题本身**。蓝漆规则、参数预扫描
不是深刻的算法设计，是 1970 年代决策被标准固化的结果。没有「更好的 C 预处理方式」这个研究方向。

**但值得花半天读懂它烂在哪**——因为它是「为什么后来的语言全都改用卫生宏
（Rust 的 `macro_rules!`、OCaml 的 ppx、Scheme 的 `syntax-rules`）」的反面教材。
对**语言设计者**来说这个「为什么」比正面教材有用。

规模参考：GCC 的 libcpp 约 4 万行 C，chibicc 的教学级实现约 1000 行。

### MIPS：完全不碰

**2026-08-05 查证**：MIPS 公司 2021 年就宣布放弃自家 ISA 转投 RISC-V，
2025 年 7 月 GlobalFoundries 宣布收购 MIPS——收购的是它的 **RISC-V** IP。
**这个 ISA 连亲爹都不做了**，学它的代码生成零迁移价值。

## 关于用 LLM 加速：边界在哪

用户明确的策略是**用 LLM 跳过没有价值的问题**。这个策略成立，但边界要清楚。

### LLM 已经压塌的（放心用）

- ISA 语义、调用约定、ABI 细节查询
- 工具链噪音（opam/dune/链接器报错、ABI 不匹配）
- 规范文本解读（C 标准条款、LLVM IR 语法）
- 样板代码（AST 打印器、访问器骨架、测试脚手架）
- 跨语言翻译（「OCaml 这么写，C++ 的惯用法是什么」）

### LLM 压不动的（必须自己长）

1. **调试自己编译器生成的错误代码**——LLM 看不到你编译器的内部状态。
   codegen 吐出 500 行错误汇编时，「哪个 pass 埋的雷」得自己找。
2. **设计决策**——LLM 会给你**一个**合理答案，但你**无法评估它好不好**，除非已有判断力。
3. **知道该问什么** ← 最大的一条。编译器领域的典型困难是「不知道存在这个概念」，
   而 LLM 对没被提出的问题是沉默的。
4. **验证正确性**——LLM 会非常自信地生成看起来合理但语义错误的 IR / 汇编。

### 特定的失败模式：流利但无深度

能一路把项目做出来，但没建立心智模型。**别的领域可能无所谓，编译器不行**——
因为调试编译器几乎全靠心智模型（程序段错误时，栈里没有任何线索指向你的哪个 pass）。

### 三条使用纪律

1. **LLM 用于「查」，不用于「替你想」。** 分界线：答案是**一个事实**就直接问；
   答案是**一个判断**就先自己给方案，再让 LLM 挑毛病。
2. **卡住时先自己撑 15–20 分钟再问。** 低于这个时长就问会跳过形成直觉的那一步。
3. **反过来用**：做完一个 pass，让 LLM **出反例考你**
   （「给我 3 个能打破我这个常量传播实现的输入」）。这是最被低估的用法。

## 2026 年行业现状（查证于 2026-08-05）

- **MLIR 是当下最抢手的编译器框架**，其次 LLVM、TVM、XLA
- 需求最旺的是 **AI 编译器 / ML runtime**，AI 加速器层出不穷，**供不应求**
- 招聘明确要求 **IR 设计能力**、计算机体系结构、跨层次性能推理
- ⚠️ **这些岗位普遍要求 C++（外加 Python/CUDA），不是 OCaml**

这不否定用 OCaml 学的路线——**概念是跨语言的**，用 OCaml 学会 SSA 和数据流分析之后
换到 C++ 是工具问题不是认知问题，反过来则不成立。代价是最后要额外花时间适应 C++ 工程环境。
