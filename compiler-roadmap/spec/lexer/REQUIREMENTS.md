### 3.2 ⭐ 记录里那条「特性没定，词法分析器写了也是白写」**对本次范围基本不成立**

`compiler/README.md` 的动工条件 1、决策 `003` 的结尾、`compiler-roadmap/CLAUDE.md`
都写着同一句话：

> 「**token 集是特性集的直接产物**，特性没定，词法分析器写了也是白写。」

**这句话对「他们自己那门语言的 lexer」成立，对「标准 C 的 lexer」基本不成立。** 理由：

- **C 的 token 集来自 C 标准，不来自他们的取舍。** 关键字、标识符、整数/浮点/字符/字符串
  字面量、标点符号（含三元、复合赋值、`->`、`...`）这些是**标准定死的**
- 决策 `003` 点名要砍的那批（**声明符螺旋规则、整型提升规则表、数组/函数退化**）
  **全部属于语法/语义层，不产生也不消灭任何 token**
- 「自选扩展」将来若引入新关键字或新运算符，**是往 token 表里加行，不是推翻结构**

**唯一的真例外是 `typedef` 与 lexer hack** —— 那一条确实横跨词法和语法，见 4.3。

> **结论**：把范围定成「**C 的词法**」时，特性集未收敛**不构成阻塞**。
> 把范围定成「**我们那门语言的词法**」时，它仍然是阻塞。
> **→ 所以第 5 节的第一个问题（范围）必须先答，它决定了这条阻塞成不成立。**

## 4. 已实测的事实约束（2026-08-25 在 `ubuntu24-pc` 上跑的，不是推测）

### 4.1 `gcc -E` 的产出规模

用一个两行的 hello world（`#include <stdio.h>` + `main`）实测：

| | |
|---|---|
| 原始 `.c` | **2 行** |
| `gcc -E` 之后的 `.i` | **815 行** |

**约 400 倍。** 这意味着**任何拿真实 `.i` 当输入的测试，第一份样本就不是小样本**。

### 4.2 `.i` 里有行标记，**它们不是 C token**

同一个文件里出现 **118 条**形如：

```
# 0 "hello.c"
# 0 "<built-in>"
# 1 "/usr/include/stdc-predef.h" 1 3 4
# 1 "hello.c"
```

**词法分析器必须显式处理它们**（识别并消费掉，通常还要用来维护「当前文件名 + 行号」
以便报错时指回原始 `.c` 而不是 `.i`）。

⚠️ **这正是 `compiler-roadmap/notes/OPEN-QUESTIONS.md` 的 Q5，至今 ⬜ 未决。**
本次设计**必须**回答它 —— 它不再是「不急」的问题了。

### 4.3 ⚠️⚠️ 「预处理过的 C」**不等于「更简单的 C」**

同一个 hello world 的 `.i` 里：

| 出现的东西 | 次数 |
|---|---|
| `__attribute__` | **87** |
| `__restrict` | **64** |
| `typedef` | **80** |
| `__builtin_va_list` | **1** |

**这些大多不是 ISO C，是 GNU 扩展。** 直接后果：

- **一个只认 ISO C 的词法分析器，在 hello world 上就会挂** —— 因为系统头文件里全是这些东西
- `typedef` 出现 80 次，说明**只要吃真实系统头，`typedef` 就绕不开**，
  而 `typedef` 正是 **lexer hack** 的来源（`T * x;` 到底是声明还是乘法，
  纯词法层分不出来）。决策 `003` 把 lexer hack 列为「可砍」，
  **但「砍掉它」和「吃真实 `.i`」这两个目标是有张力的**

> **给设计任务的提示（不是结论）**：常见的三条出路是
> ① 限定测试输入不含系统头（`-nostdinc` 或自备极小 header）、
> ② 词法层认识并跳过 GNU 扩展关键字、
> ③ 把 `typedef` 消歧留给后面的层。**选哪条是设计任务的事，这里只指出它必须被选。**
