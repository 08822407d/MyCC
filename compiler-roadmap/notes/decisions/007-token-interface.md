# 007. token 定义生成自 `tokens.mly`；token 不带位置；字面量存原始拼写；拼接推给 parser

> **状态**：✅ 已定（**带用户预留的复议条件**，见末节）
> **日期**：2026-08-26（`ubuntu24-pc`）
> **依据来源**：我的建议，**用户整体确认**
> （原话「都暂时先按你推荐的方案做，以后我懂得多了有自己的设计时可以再改」）

## 背景

L5（输出形态）和 L6（位置信息）是同一个决定的两面：词法器以什么接口交给未来的 menhir、
token 数据结构长什么样。讨论中另冒出一条新问题：翻译阶段 6（相邻字符串拼接）归谁——
实测确认 `"a" "b"` 原样保留在 `.i` 里，阶段 6 是我们的责任。

## 结论

1. **交付物 = 库 + 薄 CLI**（token 转储器——它同时就是验收工具，见决策 008）
2. **token 类型单一事实来源**：`tokens.mly` 只写 `%token` 声明，
   用 `menhir --only-tokens` 生成 Tokens 模块；将来真语法文件用
   `--external-tokens Tokens` 导入；unused 告警用 `--unused-tokens` 压
   （三个开关 ✅ 2026-08-26 在 menhir 20260209 上查证）
3. **token 不带位置**：menhir 固定接口是 `Lexing.lexbuf -> token`，
   位置从 lexbuf 读（`$startpos` / `$endpos`）；塞进 token 的位置 menhir 也不会用
4. **字面量 payload = 原始拼写**（`INT_LIT of string` 等；前缀含在拼写里）：
   转义序列（阶段 5）**不展开**；数值分类归语义层（`0777` 的八进制解释、
   `0xFFFFFFFF` 的类型判定都是目标相关的语义层规则，词法层没有做判断所需的信息）
5. **相邻字符串拼接（阶段 6）推给 parser**（`STRING+` 一行文法）；
   词法器保持无状态、无前看，token 流转储忠实于输入

## 理由

1. C17 token 约 100 个量级，手写 `Token.ml` + 将来 `.mly` 的 `%token` 要抄两遍且必须一致——
   单一来源值一行 dune 配置
2. 「不带位置」与决策 006 的行映射表严丝合缝；token 保持纯变体，好打印、好比较、好测
3. 原始拼写是 T2 往返测试的前提（`1LL` 丢后缀类型就变）；报错时显示用户原文；
   「超出类型范围」这类错误本就该语义层报
4. 拼接推给 parser 后，转储能看见输入里真实的两个字面量——
   本阶段最需要的就是「看见词法器到底切出了什么」

## 代价 / 放弃了什么

- 生成的 Tokens 模块不能改，`to_string` 要另开 `token_debug.ml`
- 词法阶段的构建链里就要有 menhir（备选 B 可以没有）
- 转义 / 数值每次使用要重新解析（要紧再缓存）
- 阶段 6 严格说没在词法层完成，记入「明确不做」清单

## 备选项（为什么没选）

| 选项 | 为什么没选 |
|---|---|
| 手写 `Token.ml`（词法阶段零 menhir 依赖） | 100+ token 两份清单人肉同步。站得住，输给「单一来源」半个身位 |
| token 自带 `{kind; loc}` | 与 menhir 接口重复，每个 token 多拖一份数据 |
| 拼接在词法层做 | 需要前看 + 处理「行标记夹在两个字符串之间」；转储不忠实 |
