# 002. 不实现 C 预处理器，用现成的 `gcc -E`

> **状态**：✅ 已定
> **日期**：2026-08-05 立，**2026-08-21 用户主动重申**（他的原话大意：
> 「不包括预处理器，预处理器就用现有提供的就行，没有必要再自己设计一遍」）
> **依据来源**：用户自述 + `ROADMAP.md`

## 背景

C 的编译流水线第一步是预处理。要不要自己实现，是划范围时躲不掉的第一个问题。

## 结论

**不实现。** 编译器**吃预处理之后的 `.i` 文件**：

```bash
gcc -E foo.c -o foo.i     # 现成的预处理器
./mycc foo.i              # 我们的编译器从这里开始
```

**边界**：这条只管「不自己实现」，**不代表不用了解它**（见下）。

## 理由

**它的复杂度全部来自向后兼容，不来自问题本身。**
蓝漆规则（blue paint）、参数预扫描这些不是深刻的算法设计，
是 1970 年代的决策被标准固化的结果。**没有「更好的 C 预处理方式」这个研究方向。**

规模参考：GCC 的 libcpp 约 4 万行 C；chibicc 的教学级实现约 1000 行。
⚠️ 这两个数字是 2026-08-05 凭知识写下的，**未查证**。

## 代价 / 放弃了什么

- 拿不到「宏展开 / 条件编译 / `#include` 搜索路径」的一手实现经验
- 测试用例得先过一遍 `gcc -E`，**多一个外部依赖**（gcc 15.2.0 已装）

## 但值得花半天读懂它烂在哪

`ROADMAP.md` 保留了这一条：预处理器是「**为什么后来的语言全都改用卫生宏**」
（Rust `macro_rules!`、OCaml ppx、Scheme `syntax-rules`）的反面教材。
**对语言设计者来说这个「为什么」比正面教材有用。**

## 影响到的其他东西

- **词法分析器的输入是 `.i` 不是 `.c`** —— 不用处理 `#` 指令，
  但**要处理 `# 1 "foo.c"` 这样的行标记**（⚠️ 这一条还没细想，见 `OPEN-QUESTIONS.md`）
- 决策 003（C 子集 + 扩展）里，**「加什么扩展」不包括宏系统**——除非哪天专门推翻这条

## 复议条件

如果最终形态转向「语言设计」方向、并且想做**卫生宏**，
那属于另起炉灶设计一套新东西，**不是回头实现 C 的那套**。
