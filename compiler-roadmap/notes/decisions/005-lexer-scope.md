# 005. 词法分析器：完整 C17 词法，输入只认 `.i`

> **状态**：✅ 已定
> **日期**：2026-08-26（`ubuntu24-pc`）
> **依据来源**：用户选项作答（`c-lexer` 设计任务，L1 / L2a / L2b 三轮逐条拍板）

## 背景

2026-08-25 用户重启词法分析器计划（有意推翻 08-21 的「不急」，见
`../../spec/lexer/REQUIREMENTS.md` §3.1）。该文件第 5 节列了 8 个开放问题，
L1（范围）决定其他一切：范围定成「自家子集的词法」，则「特性没定 = 白写」的阻塞成立；
定成「C 的词法」，阻塞不成立。

## 结论

- **范围 = 完整 C 词法，版本对标 C17**（44 个关键字；C17 词法 ≡ C11，✅ 2026-08-26 查证）
- **输入只认 `gcc -E` 产出的 `.i`**。未预处理输入按错误处理，并显式诊断
  「输入似乎未经预处理，请先 gcc -E」（探测规则见 `../../spec/lexer/DESIGN.md` §2）
- **不做**：注释、行接续（`gcc -E` 已做，✅ 实测）、三元符（gcc 默认自己都不替换 ✅ 实测；C23 已删）
- **做**：双字符组（✅ 实测原样漏进 `.i`）、二进制字面量 `0b`
  （**唯一有意偏离严格 C17 之处**；gcc 默认 `gnu17` 与 `-std=c17` 均静默放行 ✅ 实测；
  用户内核开发中常用，知情选择）
- **GNU 扩展在词法层不需要特判**：`__attribute__` / `__restrict` / `__asm__` 等
  全是合法 ISO 标识符词素（✅ 实测：零 GNU 知识的严格 ISO 词法器把 4901 行 `big.i`
  完整切完零错误）。它们是 **parser 的问题**，本决策不欠账（原 L3 就此消解）

**边界**：只管词法层认什么。语言子集的取舍（决策 003）不受影响——砍的位置从 lexer 移到
parser，报错从「不认识的词」变成「本语言不支持 X」（严格更好）。

## 理由

1. **（用户）输入是 AI agent 按需生成的源码，内容可控**，不担心词法器收到多余内容
2. **（用户）子集词法会跟不上学习用编译器的渐进丰富**，反复回头扩展太麻烦
3. **（用户）C 是被广泛使用多年的语言，对 AI 来说实现完整词法比实现子集更简单**——
   完整 C 的词法规范被标准外部钉死（附录 A 有现成词法文法），可逐条对照；
   「子集」的规范现在还不存在，让 AI 实现等于让它替用户做设计决策
4. 词法器工作量与范围几乎无关：差别只在表行数 + 浮点字面量；
   难点（数字最长匹配、转义、位置跟踪、行标记）两边完全相同
5. **与特性集彻底解耦**：token 集来自 C 标准，特性集怎么收敛 `.mll` 都不用改——
   「特性没定写了也是白写」对此范围不成立（REQUIREMENTS §3.2 的判断，已被实测支持）

## 代价 / 放弃了什么

- menhir 侧将有一批永远用不上的 token（`--unused-tokens` 可压，✅ 2026-08-26 查证）
- **「明确不做」清单必须写死防滑坡**（→ `../../spec/lexer/DESIGN.md` §1），否则「完整」没有终点
- `0b` 让「严格 C17」这句话打折扣（用户知情选择）
- 将来若迁 C23：`bool` / `true` / `false` / `nullptr` 等**普通标识符形状**的关键字
  有兼容成本（加行不改结构，彼时再议）

## 备选项（为什么没选）

| 选项 | 为什么没选 |
|---|---|
| 标准完备主义（三元符 / UCN / 宽字符全做） | 真实 `.i` 与 AI 生成代码里一次都不出现，无测试输入可覆盖；纯为「完备」一词服务 |
| 自家子集语言的词法 | 与「输入是 `.i`」前提直接冲突（真实 `.i` 必然含全量 C）；「白写」阻塞复活；被测物和测例都出自己手，无外部校验 |
