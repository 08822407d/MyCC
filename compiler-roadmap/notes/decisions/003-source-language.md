# 003. 源语言 = C 子集 + 自选扩展

> **状态**：✅ 已定
> **日期**：2026-08-21（`ubuntu24-pc`）
> **依据来源**：**用户选项作答**（我给了三个候选，他选了这个）

## 背景

用户 2026-08-21 交代项目定位时说：现在最要紧的是想清楚
「**实现的这个编译器要支持哪些特性**」，这需要一段较长的问答和资料收集。

但在开始逐条挑特性之前，有个更前置的岔路必须先定：
**「要支持哪些特性」到底是一道选择题还是一道设计题？**
—— 如果范围由一本书钉死，那是选择题；如果语言是自己设计的，那是设计题。
**两者对应的资料收集方向完全不同**，不先定就没法开工。

## 结论

**以 C 为底，自己决定砍掉什么、加上什么。**

用户选项原文：

> **C 子集 + 自选扩展** —— 以 C 为底，自己决定砍掉什么（如声明符螺旋、typedef 歧义）、
> 加什么。既有参照物又有设计空间，测试集能部分复用。

**边界**：这条只定了「**语言形态是 C-like，且我有取舍权**」。
**具体砍什么、加什么，一条都还没定**（→ `notes/feature-inventory.md`）。

## 理由

1. **有参照物**：C 的语义已经被写死过一遍，不用从零发明；
   遇到「这里该怎么定」时永远有一个已知答案可参考
2. **有设计空间**：C 里有一批**纯历史包袱**的东西
   （声明符螺旋、typedef 导致的 lexer hack、整型提升规则表、数组/函数退化），
   学它们学到的是「C 的规定」不是「编译器的原理」，**有权砍掉**
3. **测试集能部分复用**：Nora Sandler 那本书的配套测试集是语言无关的
   （Python 3.8+ 脚本），砍掉的部分对应的用例跳过即可
4. **用户是 C 专家** —— 在自己最强的语言上做取舍，
   他有能力判断「这条规则到底解决了什么问题」，这是普通学生给不了的输入

## 代价 / 放弃了什么

⚠️ **这是三个选项里最容易失控的一个。** 放弃了「书把范围钉死」带来的保护：

- **范围会漂**。写着写着想加特性，是这类项目最常见的死法
- **测试集只能部分复用**，加的扩展要自己写用例
- **每个取舍都要花时间论证** —— 这正是当前这轮设计问答的成本

**对冲手段**（写在这里，将来失控时回来看）：
每个特性进入清单必须回答「**它逼我实现哪个编译器机制**」，
**答不出来的一律不要**（→ `feature-inventory.md` 的填写规则）。

## 备选项（为什么没选）

| 选项 | 为什么没选 |
|---|---|
| **C 子集，范围由书钉死**（Nora Sandler《Writing a C Compiler》增量推进） | 这是 `ROADMAP.md` 阶段 1 原来写的方案。范围最稳、设计问答量最小，**但用户明确想要设计空间** |
| **自己设计的新语言**（语法/类型系统全自定，C-like 但不受 C 标准约束） | 自由度最大，但没有参照物、没有现成测试集，**在编译器理论还是初学者的阶段风险过高** |

## 影响到的其他东西

- 🔴 **`ROADMAP.md` 阶段 1 的表述要改** —— 那里写的是「**为什么用书而不是自己划范围**」，
  现在的定位降级为「**书是范围参照物和测试集来源，不是权威**」。
  2026-08-21 只在阶段 1 加了指向本篇的说明，**正文等特性集收敛后统一重写**
- **决策 002 仍然成立**：不做预处理器，「加扩展」不包括宏系统
- 词法分析要等这条落实到具体特性表之后才动手 —— **token 集是特性集的直接产物**

## 复议条件

如果特性集讨论了两三轮还收不拢、或者范围明显在漂，
**退回「按书钉死」是一条有效的止损路径**，不丢人。
