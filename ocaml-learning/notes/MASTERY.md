### 2026-08-04 详细（第一批真实作答数据）

**答对的：** 我给了 A/B 二选一（`let x = 5 in ((let x = 6 in x) + x)` 是 12 还是 11），
他选 **B（11）**，理由是「x=6 的作用域仅在最内层括号里」。**结论和理由都正确。**

**主动自我纠正（最有价值的一条）：** 他补了一句
> 「按照 OCaml 的真实运作原理，应该并不是覆盖值，是名称覆盖了」

这个区分是准确的，而且是他**自己提出来的**，不是被纠正后复述。
说明知识点 1（`let` 是绑定不是变量、绑完不能改）**真的进去了**，
而不只是记住了一句话 —— 这是目前为止最硬的一条证据。

**暴露的误解（已当场纠正）：** 他问「`in` 后面如果是复杂表达式，是否必须跟括号」。
方向正好反了：body 贪婪，`in` 后面**不需要**括号；括号的作用是**截断**它。
用 `2 * let x = 3 in x + 1`（=8）对 `2 * (let x = 3 in x) + 1`（=7）演示后说明了。

**主动提问的质量：** 同时问了「`in` 的结合优先级在哪一层」。
这说明他在**主动构建语法模型**，不是被动接收 —— 与他自述的学习习惯一致。

**待核对：** 留了口算题 `let x = 10 in (let x = x + 1 in x) + x`（答案 21），
考「等号右边看到的是外层绑定」。→ **2026-08-05 已答，答对，见下。**

### 2026-08-05 详细（表现最好的一天）

**自己修正假设并给出准确概括（两次）：**

1. 先提出「匿名函数没有名字，所以定义的同时就必须调用，否则找不到它」——**这个是错的**。
   给了反例（传给 `twice`、装进列表）之后，他自己重新表述为：

   > 匿名函数如果不当场使用，就需要一个手段将它以某种形式**锚定**，否则就没有途径使用它。

   **「锚定」这个词是他自己造的，而且准确**——它恰好涵盖了起名、传给别人、存进容器三种情况。

2. 复述求值规则时说「从其后取**参数个数相同**的其他值作为参数」——
   「参数个数」这个概念在 OCaml 里不成立。给了 `let f x y = x + y in f 3 → int -> int` 之后接受了。

**主动提出的高质量问题**（说明在构建模型而不是被动接收）：

- 「`in` 后面如果是复杂表达式，是否必须跟括号？」← **方向搞反了**（body 贪婪，括号是用来截断的），
  但问题本身问到了点子上
- 「`in` 的结合优先级在哪一层？」
- 「`int -> int` 里谁是参数谁是返回值？」
- 「嵌套函数是不是可以转化成多参函数来理解？」← 几乎答对，只差「两层 fun 之间夹计算」那个例外

**自己提出的类比：**「像 C 的宏函数和 C 函数的区别，宏会触发多次副作用」。
**洞察是对的**（副作用次数取决于代码在哪一层），**但对应错了位置**——
C 宏是文本替换导致**参数**重复求值，OCaml 传值所以参数恰好算一次。他接受了这个修正。

**暴露的薄弱点（需要后续巩固）：**

- **「绑定 vs 赋值」还没完全内化**：问「要赋值就得用 `let` 吗」，说明还在用「赋值」的框架理解 `let`。
  已经讲了 `ref`/`:=`/`!` 做对比，但**这一条值得在讲不可变性时再压一遍**。

**元认知层面（重要，影响怎么教）：**

他主动提出「有些卡很久的问题没有技术含量，纯粹是知识面不够，在这种问题上钻很久没有价值」，
并据此要求调整学习路线。**这是深思熟虑的策略判断，不是偷懒**，而且他用这个论点
正确推翻了我的一条建议。详见 `compiler-roadmap/ROADMAP.md` 的「关于用 LLM 加速」。

**那道口算题终于收到了，答对：** `let x = 10 in (let x = x + 1 in x) + x` → 他答 **21**，正确。
这题考两件事，答对说明两件都通了：

1. 里层 `let x = x + 1` 等号右边那个 `x` 用的是**外层的 10**（新绑定要到 `in` 之后才生效）→ 里层 11
2. 括号外的 `+ x` 已经出了遮蔽范围，拿到的是**外层的 10**（呼应他 08-04 自己说的「名称覆盖」）

⚠️ 只给了数字，**没给推导过程**，所以不能排除是蒙对或心算时走了别的路。
不过和 08-04 那次（选 11 并说得出理由）连起来看，遮蔽这一块**大概率是真通了**。

### 2026-08-05 后半程 — 柯里化那一问 + 一个行为观察

**柯里化那一问，答得干净利落。** 我拿公开课代码里的 `String.concat "\n"` 问
「只给第一个参数会得到什么」，他答：

> 它会变成一个期待输入字符串列表且返回字符串的另一个函数

**完全正确**（实测 `val join_lines : string list -> string = <fun>`），而且用的是
**类型语言**在描述，不是"少给一个参数"这种操作性描述。当场把「柯里化」这个词给了他。

**他自己提出的问题质量继续走高**（都在知识点 6 里）：

- 「`(program: string)` 外面那对括号是必须的吗，为什么」← **问到了语法本质**，
  不是问"怎么写"而是问"为什么必须这么写"
- 「`: type` 是『指定该表达式的类型，而不是自动推断』吗」← 只差一个字，
  说明他已经在区分"推断"和"约束"两种机制，只是还没意识到**两者是同时在跑的**
- 「`program` 是不是对应命令行参数 / C 的 argc+argv」← **猜错了**，
  但错得有道理（那个玩具的"源程序"恰好就是个数字）。纠正后没有再纠结。

**→ 记进行为准则：他的好奇心会把话题一路带向深处，但他自己知道什么时候该停。
我的责任是在深度开始超出「能用」之前主动收网，而不是等他喊停。**

**顺带说明这不是"学不动"**：在踩刹车之前的那几轮里，他连续做出了**三次高质量的判断**：

1. 指出 `let f x : int = …` 反直觉，理由是「人会按自然语言习惯把冒号两边关联起来」
   —— **准确命中了这个语法糙点的心理成因**。
2. 追问「为什么不把类型断言紧跟在函数名后面，是因为函数名不是一个表达式或者值吗」
   —— 猜的原因不对（真因是后缀类型语法占了地盘），**但「定义位置 vs 使用位置」这个
   区分本身是对的且重要的**，他是自己想到的。
3. 指出「作用在 `f x` 上就好像遵循的不是定义时的逻辑，而是使用时的逻辑」
   —— **这一条基本命中了 ML 系语法的设计要点**（`let f x = e` 是等式不是声明，
   左边就是使用式）。我只需要纠正他附带的「或者说就像是运行时的行为」——
   那是**编译期的全称命题**，不是运行时。

**部分正确、需要纠正的一次**：他总结「对函数签名的类型断言就是这个值的类型断言」——
**机制说对了，但这句是错的**：`let f x : int = 5` 里 `f` 的类型是 `'a -> int` 不是 `int`。
只有冒号左边光是 `f` 不带参数时，才是对 `f` 这个值本身的断言。已当场纠正并给了证据。
另外他把 `f x` 叫「函数签名」，**这个词在 OCaml 里被占用了**（指 `.mli` 的模块接口），也纠正了。
