### 2026-08-04 详细（第一批真实作答数据）

**答对的：** 我给了 A/B 二选一（`let x = 5 in ((let x = 6 in x) + x)` 是 12 还是 11），
他选 **B（11）**，理由是「x=6 的作用域仅在最内层括号里」。**结论和理由都正确。**

**主动自我纠正（最有价值的一条）：** 他补了一句
> 「按照 OCaml 的真实运作原理，应该并不是覆盖值，是名称覆盖了」

这个区分是准确的，而且是他**自己提出来的**，不是被纠正后复述。
说明知识点 1（`let` 是绑定不是变量、绑完不能改）**真的进去了**，
而不只是记住了一句话 —— 这是目前为止最硬的一条证据。

**暴露的误解（已当场纠正）：** 他问「`in` 后面如果是复杂表达式，是否必须跟括号」。
方向正好反了：body 贪婪，`in` 后面**不需要**括号；括号的作用是**截断**它。
用 `2 * let x = 3 in x + 1`（=8）对 `2 * (let x = 3 in x) + 1`（=7）演示后说明了。

**主动提问的质量：** 同时问了「`in` 的结合优先级在哪一层」。
这说明他在**主动构建语法模型**，不是被动接收 —— 与他自述的学习习惯一致。

**待核对：** 留了口算题 `let x = 10 in (let x = x + 1 in x) + x`（答案 21），
考「等号右边看到的是外层绑定」。**他还没答**，下次开工先收这个。

### 2026-08-05 详细（表现最好的一天）

**自己修正假设并给出准确概括（两次）：**

1. 先提出「匿名函数没有名字，所以定义的同时就必须调用，否则找不到它」——**这个是错的**。
   给了反例（传给 `twice`、装进列表）之后，他自己重新表述为：

   > 匿名函数如果不当场使用，就需要一个手段将它以某种形式**锚定**，否则就没有途径使用它。

   **「锚定」这个词是他自己造的，而且准确**——它恰好涵盖了起名、传给别人、存进容器三种情况。

2. 复述求值规则时说「从其后取**参数个数相同**的其他值作为参数」——
   「参数个数」这个概念在 OCaml 里不成立。给了 `let f x y = x + y in f 3 → int -> int` 之后接受了。

**主动提出的高质量问题**（说明在构建模型而不是被动接收）：

- 「`in` 后面如果是复杂表达式，是否必须跟括号？」← **方向搞反了**（body 贪婪，括号是用来截断的），
  但问题本身问到了点子上
- 「`in` 的结合优先级在哪一层？」
- 「`int -> int` 里谁是参数谁是返回值？」
- 「嵌套函数是不是可以转化成多参函数来理解？」← 几乎答对，只差「两层 fun 之间夹计算」那个例外

**自己提出的类比：**「像 C 的宏函数和 C 函数的区别，宏会触发多次副作用」。
**洞察是对的**（副作用次数取决于代码在哪一层），**但对应错了位置**——
C 宏是文本替换导致**参数**重复求值，OCaml 传值所以参数恰好算一次。他接受了这个修正。

**暴露的薄弱点（需要后续巩固）：**

- **「绑定 vs 赋值」还没完全内化**：问「要赋值就得用 `let` 吗」，说明还在用「赋值」的框架理解 `let`。
  已经讲了 `ref`/`:=`/`!` 做对比，但**这一条值得在讲不可变性时再压一遍**。

**元认知层面（重要，影响怎么教）：**

他主动提出「有些卡很久的问题没有技术含量，纯粹是知识面不够，在这种问题上钻很久没有价值」，
并据此要求调整学习路线。**这是深思熟虑的策略判断，不是偷懒**，而且他用这个论点
正确推翻了我的一条建议。详见 `compiler-roadmap/ROADMAP.md` 的「关于用 LLM 加速」。
