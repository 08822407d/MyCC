## 10.1 切入点：从「等号右边看不见自己」接上

用户 2026-08-05 答对过这道题（答 21）：

```ocaml
let x = 10 in (let x = x + 1 in x) + x
```

考点就是**普通 `let` 的等号右边看到的是外层绑定**。现在让这条规则挡一次路：

```ocaml
let countdown n = if n <= 0 then 0 else countdown (n - 1)
Error: Unbound value countdown
Hint: If this is a recursive definition, you should add the rec keyword
```

> **`rec` 干的事只有一件：让等号右边也能看见正在定义的这个名字。**

## 10.2 ⭐ 用户的困惑（很有价值，一定要复用这个讲法）

他说：

> 「`let rec x = x + 1` 像是用新 x 覆盖旧 x，受传统命令式语言惯性思维影响，
> 看这一段就好像仅仅是做了一次简单的递增。但因为提到了 rec……就会变迷惑。」

**这个观察精确指向了 `rec` 到底改了什么。** 用这一对来解，只差三个字母：

```ocaml
let x = 5 in let     x = x + 1 in x    →  6        ✅
let x = 5 in let rec x = x + 1 in x    →  Error    ❌
```

| | 等号右边的 `x` 指向 |
|---|---|
| 不带 `rec` | **外层那个**（值 5）→ 算出 6，绑给一个新的 `x`（**遮蔽**，不是自增） |
| 带 `rec` | **正在定义的这个**（还没有值）→ 循环，编译器拒绝 |

**他的直觉是对的**：不带 `rec` 那个确实能工作，结果 6 正是「自增」直觉预期的数。
只是机制是遮蔽——**结果碰巧一样，过程完全不同**。而 `rec` 恰恰是把这个能工作的写法变成不可能的开关。

**为什么会别扭**：C# 里 `x = x + 1` 只有一个 `x`，「右边指向谁」根本不是问题；
OCaml 里每个 `let` 都造新名字，所以这是个**必须回答的问题**，默认答案是旧的，`rec` 改成新的。
**C# 没有这个开关，因为它没有这个问题。**

## 10.3 `rec` 能用在什么上（用户主动问的）

语法上能写在任何 `let` 上，但编译器会拒绝一部分右边（**全部实测**）：

| 右边是什么 | 允许？ | 例子 |
|---|---|---|
| **函数** | ✅ | `let rec f n = … f (n-1) …` |
| 没引用自己的任何东西 | ✅（`rec` 白写） | `let rec x = 5` |
| **要立刻算出结果的表达式** | ❌ | `let rec x = x + 1` |
| 「构造」出来的结构 | ✅ | `let rec ones = 1 :: ones`（无限循环列表，取第 7 个是 1） |

**判据：右边能不能「先占个位子，之后再填」。**

- 函数：定义时只是记下代码**不执行** → 调用时名字早就有了 ✅ ← **这是知识点 8 的直接应用**
- 构造：先分配格子再把自己填进去 → 和 C 里 `node->next = node` 造环形链表一回事 ✅
- 计算：必须当场得出一个数，而那个数依赖自己 → 无解 ❌

> **实践上只跟函数用。** 第 4 行那种「递归的值」极其罕见。
> 见到 `This kind of expression is not allowed as right-hand side of let rec`
> 就是「你想 rec 的东西不是函数」。

**C# 对照**（对应得很整齐）：方法天生可自引用不需要关键字，字段不行（`int x = x + 1;` → CS0165）。
区别只是 OCaml 要你把 `rec` 写出来——**代价换来的是一眼能看出哪些函数是递归的**。

## 10.4 基准情形 / 递归情形

> **基准情形（base case）** — 不再递归、直接给出答案的那一支。**递归的出口。**

> **递归情形（recursive case）** — 把问题**变小一点**，然后交给自己。

```ocaml
let rec sum n =
  if n <= 0 then 0            (* 基准情形 *)
  else n + sum (n - 1)        (* 递归情形，n 变小了 *)
```

展开（用户答对了 `sum 4 = 10`）：

```
sum 4 = 4 + (3 + (2 + (1 + 0)))
                            ↑ sum 0 命中基准情形，不再往下
```

**两条硬性要求，缺一个就栈溢出**（实测 `Stack overflow during evaluation (looping recursion?)`）：

1. 必须有基准情形
2. **每次递归必须朝基准情形靠近** ← 容易忽略。写了出口但参数不朝它走（`sum (n+1)`）照样溢出

**C 循环对照**：`for (i = n; i > 0; i--)` —— 循环条件 ≈ 基准情形，`i--` ≈ 让问题变小。
**同样两件事，C 写在 `for` 头部，OCaml 拆成 `if` 的两支。**

> 「递归代替循环」不是「递归更好」，是**在 OCaml 里递归就是循环的写法**——
> 没有可变的循环计数器可用（知识点 8：默认不可变）。

## 10.5 ⚠️ 重要发现：`if` 和 `let … in` 在「后面的 `;`」上行为相反

练习 `countdown` 时撞出来的，**这是个必须记住的不对称**：

| 结构 | 后面的 `; 下一句` 归谁 |
|---|---|
| `let x = 1 in A; B` | **归 body**（`A; B` 都在 `in` 里面） |
| `if c then A else B; C` | **不归 else**（`C` 在 `if` 外面，**无条件执行**） |

实测证据：

```ocaml
let f b = if b then print_string "[then]" else print_string "[else]"; print_string "[C]"
f true   →  [then][C]
f false  →  [else][C]        ← [C] 两种情况都打印
```

**后果**：`countdown` 写成下面这样会**无限循环**，因为基准情形被架空了：

```ocaml
if n <= 0 then () else print_int n;  countdown (n-1)
└────────── if 只管这里 ─────────┘  └── 永远执行 ──┘
```

`n <= 0` 时确实没打印，但**照样**调用 `countdown (n-1)`，n 一路减到负数。

**正解**：

```ocaml
let rec countdown n =
  if n <= 0 then ()
  else (print_int n; countdown (n - 1))     (* → 打印 321 *)
```

> **`if` 的分支里要放多句必须自己加括号**（或 `begin … end`）。
> 这是第三次撞上「后面还有东西时该归谁」——前两次是嵌套 `match`、`match` 后接 `;`。
> **判据没变：不确定就加括号。**

## 10.6 尾递归（2026-08-07 讲完）

切入点是**同一台机器、同一个数、一个炸一个不炸**（全部实测）：

```ocaml
let rec sum     n     = if n <= 0 then 0   else n + sum (n - 1)
let rec sum_acc acc n = if n <= 0 then acc else sum_acc (acc + n) (n - 1)
```

```
sum     100_000_000    →  Stack overflow during evaluation
sum_acc 0 100_000_000  →  5000000050000000        ← 秒出
```

> **尾调用（tail call）** — 函数体里「最后一件事」就是调用另一个函数，
> 调用的结果**直接**当自己的返回值，中间不再加工。
>
> **尾递归（tail recursion）** — 尾调用的对象是自己。

**判据：递归调用回来之后还有没有活干。** 有 → 那一帧必须留着 → 累积 → 溢出。

### ⭐ 用户的疑问很值钱，一定复用

他判断 `1 + len rest` 不是尾递归（**对了**），但补了一句：

> 「我不是很确定，因为这个加的是一个**常数**，而不是参数。」

**当场实测打掉这个疑虑**（把 `sum` 的 `n +` 换成 `1 +`，其余不变）：

```ocaml
let rec count n = if n <= 0 then 0 else 1 + count (n - 1)
count 100_000_000   →   Stack overflow        ← 照样炸
```

**栈帧不是为了存那个 `1` 才留下的**——`1` 是立即数，编译进指令，一字节不占。
真正留下栈帧的是**「调用回来之后还得回到我这儿」这件事本身**。C 对照一次讲通：

```c
return 1 + len(rest);        /* len 必须 ret 回我这帧，我才能做加法 → 返回地址必须压栈 */
return len_acc(acc+1, rest); /* 我没有后续动作 → 可以先拆自己这帧，call 退化成 jmp */
```

> **判据不是「多做的事有多大」，是「还有没有事」。** 只剩一条 `inc` 那帧也得活着。

不是尾递归的常见形状：`1 + f x`、`f x + f y`、`- (f x)`、`(f x) :: []`。

### 用户当场写的练习（两个错，都典型）

他写：`let rec count_acc acc n = if n <= 0 then 0 else rec count_acc (acc + 1) (n - 1)`

1. **`rec` 写到了调用处** → `Syntax error`。
   **`rec` 是 `let` 的一部分，不是调用的一部分**；一旦名字可见，调用它和调用 `print_int` 没区别。
   （C# 对照：声明处也不需要标「这是递归方法」。OCaml 只是把标记显式化，**同样只标一次**。）
   ⚠️ **他第二次回答时仍然没改掉这个 `rec`**——只改了基准情形。下次遇到要点明。
2. **基准情形返回 `0` 而不是 `acc`** → `count_acc 0 100` 恒等于 `0`。

**第 2 个错值得单独讲，这是累加器写法的分水岭：**

| | 答案在哪儿 | 基准情形返回 |
|---|---|---|
| `sum`（非尾递归） | 在**回来的路上**攒（`n + n + …`） | 加法的单位元 `0` |
| `sum_acc`（尾递归） | 在**去的路上**就攒好了，全在 `acc` 里 | **`acc`** |

> **去的路上攒好的东西，回来时必须交出去。** 返回 `0` 等于攒了一路然后原地销毁。

**递归情形他一次就写对了**（`(acc + 1)` 在调用之前算完）——那才是这题真正要练的，
**纠正时先说这句**。

## 10.7 藏起累加器：内部辅助函数与闭包

`count_acc 0 n` 里那个 `0` 是**实现细节**，不该让调用方记。社区标准写法是套一层壳：

```ocaml
let count n =
  let rec go acc n = if n <= 0 then acc else go (acc + 1) (n - 1) in
  go 0 n
```

- **`go` 是惯例名**，同类还有 `aux`、`loop`。看到就知道「这是藏起来的递归实现」。
- `let rec go … in go 0 n` —— **`in` 后面那句才是 `count` 的返回值**。
- C# 对照：**C# 7 的 local function**，形状几乎一样。
  ⚠️ **但 .NET 的 JIT 不保证尾调用优化**，同样的写法传一亿会 `StackOverflowException`。
  **OCaml 那个是语言级保证。** ← 这是少数「OCaml 比 C# 强出一截」且正好在他敏感方向上的点。

### 用户主动追问的作用域问题（答得完全正确）

他问 `go` 里的 `n` 是哪一个，并自答：内层是形参、只在内层有效；`go 0 n` 里的是外层的。
**他还自己加了一句「相当于两个函数定义，编译器会自动分开对待」——也对。**

```ocaml
let count n =                       (* n① *)
  let rec go acc n = … n … in       (* n②，作用域只有等号右边；这里面的 n 全是 n② *)
  go 0 n                            (* 这个 n 是 n①，已经出了 go 的身体 *)
```

**`in` 就是分界线。这是知识点 3「遮蔽」的又一次出现**——和那道答 21 的口算题同一个考点。

> 他给了一个**极好的锚**：`in` 对应数学题里的「**其中**」。
> 「解 g(x) = … f(x) …，**其中** f(x) = …」
> **这不是巧合是词源**（Haskell 干脆有个关键字叫 `where`）。**以后讲 `let … in` 直接用这个。**

### 🔴 词法作用域 vs 动态作用域（2026-08-07 快问快答第 3 题引出，**用户在这里错了**）

题目与实测：

```ocaml
let x = 3 in  let f y = x + y in  let x = 100 in  f 1     →  4    (* 他答 101 *)
let x = 3 in  let x = 100 in  let f y = x + y in  f 1     →  101  (* 只挪了定义位置 *)
```

**编译器自己把话说破了**：第一段会报 `Warning 26 [unused-var]: unused variable x`
——**那个 100 从头到尾没人用过。**

他的推理是：「`f 1` 写在 `let x = 100 in` 里面，所以 `f` 应该看得见 100。」

> **这个推理有名字，而且在有些语言里就是对的。**
>
> **动态作用域（dynamic scoping）** — 名字指向谁，由**调用发生时的环境**决定。
> **词法作用域（lexical scoping）** — 由这段代码**写在源文件哪个位置**决定。

**bash 就是动态作用域**（演示脚本 [`../side-topics/code/dyn_scope.sh`](../side-topics/code/dyn_scope.sh)）：

```bash
f() { echo "x = $x"; }
outer() { local x=100; f; }
x=3
f       # → x = 3
outer   # → x = 100      ← 同一个 f，看到的 x 变了
```

**给这个错误起名字之后他立刻就通了。** ← 讲法可复用：**先承认他的推理是一套自洽的语义，
再说明 OCaml/C/C# 用的是另一套。**

### 分离「作用域」和「求值顺序」的三个证据（用户主动追问）

他追问：`f` 绑到 3，**真正的原因是作用域，还是「`let x = 3` 在求值顺序的上游」**？
—— 好问题，因为在一条 `let … in` 链里两者**恰好重合**，那个例子分不出来。三个能分开的：

| 证据 | 现象 | 说明什么 |
|---|---|---|
| `let rec x = x + 1` | 报 *not allowed as right-hand side*，**不是** `Unbound value` | 作用域说「可见」，求值说「算不出」→ **两件事** |
| `let rec even … and odd …` | `odd` 在文本上、求值上都在后面，**照样可见** | 可见性由作用域规则说了算 |
| `let f y = z + y` / `let z = 3` | **`Unbound value z`，连编译都过不去** | **决定性**：调用时 `z` 明明有值，但编译期就判死了 |

> **两个不同的问题，别混：**
>
> | 问题 | 由谁决定 | 何时确定 |
> |---|---|---|
> | 名字**指向哪一个绑定** | **作用域**（文本位置） | **编译期** |
> | 运行到这儿**有没有值 / 值是多少** | 求值顺序 | 运行期 |

### ⭐ 交给用户的固定套路（他要的就是这个）

1. **先画名字**：每个名字往上找**文本上最近的、包着它的**绑定，连线画死
   （只有 `let rec` / `and` 会把等号右边也拉进作用域）← **编译期**
2. **再走求值**：按顺序执行，遇到名字直接读它连到的绑定 ← **运行期**
3. **完全不管优化**

> **关于第 3 条，说法要够强**：不是「初学者先别管」，而是
> **优化按定义不改变可观察行为，改变了就是编译器 bug**。
> 他要写编译器，**这正是优化 pass 的验收标准**，现在建立的习惯将来直接能用。
> ⚠️ 我提过一句「flambda 可能真把 `x + y` 化简成 `3 + y`」——**那句对解题毫无用处，
> 不该进入他的推理**，当时没说清，已补正。

### 闭包

把 `go` 的参数改名，不遮蔽时外层变量直接穿透（实测 `count 3 → 9`，即 3+3+3）：

```ocaml
let count n =
  let rec go acc m = if m <= 0 then acc else go (acc + n) (m - 1) in
  go 0 n
```

> **闭包（closure）** — 一个函数连同它「看得见的外层变量」打包成的整体。
> `go` 不只是一段代码，它还随身带着外层的 `n`。

实用价值：辅助函数要用外层的查找表 / 配置时，**不必一路当参数传下去**。

⚠️ **我在这里说错过一句、已实测纠正**：我说「C 直觉套不过来，C 的嵌套函数不能捕获」——
**错的，gcc 的嵌套函数既遮蔽也捕获，行为和 OCaml 一致**。
真正的区别在实现机制（trampoline / 可执行栈 / 生命周期），
**整段挖掘单独存档在 [`../side-topics/c-nested-functions-trampoline.md`](../side-topics/c-nested-functions-trampoline.md)**。
一句话版本：**C 里闭包活不过外层的 `return`，OCaml 里能**——所以 OCaml 的函数可以当返回值。
