# 交接自检任务书

你现在**不是在教学**，而是在给这个项目做一次上下文交接的体检。
执行完把报告写进 `notes/handoff-report.md`，然后停下，等用户回原对话核对。

## 铁律

1. **严格按阶段顺序执行，不许跳步、不许提前读文件。**
2. **如实记录。失败项照实写，不要美化。** 这份报告的唯一用途是暴露缺陷 ——
   全是 ✅ 但内容是编的，比一堆 ❌ 有害得多。
3. **全程不要动 git**，也不要修改 `notes/PROGRESS.md`、`notes/MASTERY.md`
   或任何 `docs/env/*.md`。只写报告那一个文件。
4. **不要继续教学**，不要给用户讲知识点，不要出新练习。

## 先确定命令前缀

- 当前目录下有 `scripts/ocaml.sh` → 前缀是 `./scripts/ocaml.sh`（正常情况）
- 否则有 `ocaml-learning/scripts/ocaml.sh` → 前缀是 `./ocaml-learning/scripts/ocaml.sh`
  （说明用户是在仓库根目录 `MyCC/` 打开的，这不算失败，但要写进报告的备注）

## 阶段 0 — 闭卷 ⭐ 这一阶段最重要，也最容易作弊

**在写完这一阶段的六个答案之前，禁止使用任何工具。**
不许 Read、不许 Glob、不许 Grep、不许 Bash。除了本任务书，什么都不许看。

只凭**已经自动加载进上下文的内容**（主要是 `CLAUDE.md`）回答：

| 编号 | 问题 |
|---|---|
| Q0-1 | 上次教到哪个知识点？ |
| Q0-2 | 有没有已经布置但用户还没做的练习？具体是哪个文件？ |
| Q0-3 | 现在在哪台机器上？判据是什么？ |
| Q0-4 | 构建并运行一个练习的命令长什么样？ |
| Q0-5 | 用户对教学风格提了什么要求？至少说出两条。 |
| Q0-6 | git 操作该由谁发起？ |

**不知道就写「不知道」。** 写「不知道」是有价值的观测结果 ——
它说明 `CLAUDE.md` 的进度快照漏了东西，正是这次体检要找的问题。
猜一个蒙对了反而会掩盖缺陷。

这六个答案**原文锁定**，后面阶段发现答错了也不许回头改，只能在阶段 1 里标注对错。

## 阶段 2 — 机械检查

依次执行，**记录每条命令的实际输出**，以及**有没有弹出授权确认框**：

1. `<脚本> platform`
2. `<脚本> check`
3. `<脚本> list`
4. `<脚本> run ex00_smoke` — 期望输出 `hello`
5. `<脚本> run ex01_int_float` — 期望 6 条 `[--] 还没做`，
   如果用户已经写了，则记录实际的 `[OK]`/`[XX]` 分布

判定要点：

- `platform` 那行和阶段 0 的 Q0-3 是否一致
- 有没有弹授权框（弹了 = 免授权规则没生效，要写进报告）
- 工具是否齐全，版本是否符合 `docs/env/COMMON.md` 的口径；
  **对不上要写清差在哪**，不要一句「基本一致」带过

> **关于「有没有弹授权框」这个观测**：如果本次会话是非交互模式，权限本来就可能直接放行，
> 那么「没弹框」**不能单独证明**白名单生效。这种情况要在报告里说明，
> 并改为直接核对 `.claude/settings.json` 的 allow 列表是否覆盖了阶段 2 用到的全部命令形式。

> `check` 已经把 COMMON.md 口径里的全部版本都列出来了。
> **不要为了查版本去绕过脚本手敲 `wsl -d Ubuntu -- ...` 之类的命令** ——
> 那种写法是平台相关的，在另一台机器上跑不通。如果发现 `check` 少列了什么，
> 那本身就是一条要写进「发现的问题」的缺陷，而不是自己绕过去。
